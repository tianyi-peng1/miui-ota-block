# MIUI / HyperOS 屏蔽系统更新：三项核实报告

核实时间：2026-11-03
用途：发布前事实核对

## 一、包名适用范围

**结论：`com.android.updater` 覆盖 MIUI 12 ～ HyperOS 3 全线，未发现更名。**

| 系统版本 | 包名 | 卸载风险 | 证据来源 |
|---|---|---|---|
| MIUI 12 及更早 | `com.android.updater` | **会卡米**（社区明确记录） | Universal Android Debloater 数据库 |
| MIUI 13 / 14 | `com.android.updater` | 不卡米 | 同上，原文注明 "Doesn't bootloop on MIUI 13 and above" |
| HyperOS 1 / 2 | `com.android.updater` | 不卡米，但被列入"部分机型可能开机循环"分组，建议冻结而非删除 | XDA HyperOS 2/3 精简列表（2026-01） |
| HyperOS 3 | `com.android.updater` | 实测可用 | XDA 帖 OS3.0.304.0（2026-05-17），作者用该命令阻止强制升级 |
| 国际版 / 欧洲版 | `com.android.updater` | 同上 | 多方教程一致 |

关键原文（UAD 数据库，共 5399 条包记录中该条目）：

> `com.android.updater` — **Mi Updater** — Provides system updates
> **REMOVING THIS WILL BOOTLOOP YOUR DEVICE! Doesn't bootloop on MIUI 13 and above.**
> removal: Expert

这条记录同时说明两件事：包名确为小米系统更新；**卸载的卡米分界线在 MIUI 13**。

注意：网上偶见 `com.xiaomi.updater` 的说法，本次核实**未在任何一手来源中找到该包名存在于 MIUI/HyperOS 的证据**，应视为误传。

## 二、hosts 阻断的可行性

### 2.1 域名证据（来自实际调用小米接口的开源项目）

`YuKongA/Xiaomi-Update-Info`（Python，专门查询 MIUI/HyperOS 更新信息）源码中的接口常量：

```python
MIUI_UPDATE_URL = "https://update.miui.com/updates/miotaV3.php"
DOWNLOAD_BASE_URL_ULTIMATE = "https://ultimateota.d.miui.com"
DOWNLOAD_BASE_URL_BIG = "https://bigota.d.miui.com"
```

这说明：

- 更新**检查**只走 `update.miui.com` 一个域名，路径固定为 `/updates/miotaV3.php`；
- 更新**下载**走 `bigota` / `ultimateota` 两个 CDN，与检查域名分离；
- 因此阻断 `update.miui.com` 即可让「检查 → 决定下载 → 下载 → 安装」整条链路在第一步断掉，**不需要**碰下载 CDN（碰了会连带影响主题商店）。

### 2.2 为什么 hosts 对系统组件有效

Android 的域名解析由 `netd` 处理，解析顺序是**先查 hosts 文件，再走 DNS**。`com.android.updater` 是系统应用，使用系统解析器，不自带 DoH 客户端，因此 hosts 对其生效。私人 DNS（DoT）不影响这个顺序，因为 hosts 查表发生在 DNS 查询之前。

### 2.3 置信度分级（发布时建议照此表述，不要写"100% 有效"）

| 论断 | 置信度 | 依据 |
|---|---|---|
| `com.android.updater` 是小米系统更新包名 | **高** | 多个独立来源 + 社区数据库 + HyperOS 3 实操帖 |
| `update.miui.com` 是国行更新检查接口 | **高** | 2026 年活跃项目仍在调用 |
| 阻断后「检查更新」会失败 | **高** | 机制明确，接口单一 |
| 国际版接口为 `update.intl.miui.com` | **中** | 仅见于 2022 年的模块 hosts，无近期一手证据，需实测 |
| 不存在其他备用域名 / IP 直连 | **低** | 无公开反证，但也无法证明不存在 |
| 长期有效 | **低** | 小米可随时更换接口，属对抗性变更 |

### 2.4 无法保证的部分（必须写进发布文案）

1. **小米更换 API 域名** → 模块失效。补救：抓包确认真实域名，往 hosts 补一行。
2. **updater 走硬编码 IP** → hosts 无效。目前无证据，但无法排除。
3. **与其他 hosts 模块冲突** → Magisk 的「Systemless hosts」开关、AdAway、其他 hosts 模块会互相覆盖挂载，这是本方案唯一确定会踩的坑。

### 2.5 自验方法（发布时一并给出）

```sh
su -c ping -c 1 update.miui.com        # 应解析到 127.0.0.1
su -c cat /system/etc/hosts            # 应看到模块写入的两行
```

再看「设置 → 我的设备 → 系统更新 → 检查更新」是否失败。三步都通过才算生效。

### spoliator 模块不宜推荐的实证

解包 `Xiaomi-Update-Blocker.zip` 后，其 hosts 实际内容为：

```
127.0.0.1 update.intl.miui.com
127.0.0.1 tracking.india.miui.com
127.0.0.1 api.setting.intl.miui.com
127.0.0.1 firebaseinstallations.googleapis.com
127.0.0.1 f2.market.xiaomi.com
127.0.0.1 global.market.xiaomi.com
127.0.0.1 file.market.xiaomi.com
127.0.0.1 sdkconfig.ad.intl.xiaomi.com
127.0.0.1 x-in.ls.glanceapis.com
127.0.0.1 api.accelerator.intl.miui.com
```

三个问题：

1. **没有 `update.miui.com`**，只有国际版域名，国行设备装了等于无效；
2. 屏蔽 `firebaseinstallations.googleapis.com`，会连带影响所有使用 Firebase 的应用（推送、统计）；
3. 屏蔽小米应用商店的多个域名（`f2/global/file.market.xiaomi.com`），会导致商店下载异常。
